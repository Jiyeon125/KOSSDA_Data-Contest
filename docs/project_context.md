# 프로젝트 배경지식 (Project Context)

> 이 문서는 Cursor가 이후 모든 작업에서 **먼저 참조**해야 하는 프로젝트 기준 문서입니다.
> 코드를 작성하기 전에 프로젝트의 문제의식, 데이터 역할, 분석 방향, 개발 원칙을 이 문서에 맞춰 확인합니다.
> 제안서 기반의 구체적 실험 설계·변수 매핑·**통계 검증 계획**은 [`docs/research_design.md`](research_design.md)를 함께 참조합니다.

## 1. 프로젝트 목적

본 프로젝트는 청년층의 '쉬었음' 현상을 단순 실업률로 설명하기 어렵다는 문제의식에서 출발한다.

일반적인 실업률은 구직활동을 하는 실업자를 중심으로 측정되지만, 최근 청년 문제에서는 구직활동을 하지 않고 비경제활동 상태에 머무르는 '쉬었음' 청년이 중요하게 부각된다.

따라서 본 프로젝트는 다음 질문을 중심으로 한다.

> "청년층의 쉬었음 상태는 단순한 일시적 휴식인가, 아니면 경제·주거·노동 조건이 결합된 취약성의 신호인가?"

핵심 목표는 **청년 쉬었음 집단 내부의 이질성**을 데이터로 구분하고, **취약성이 높은 하위 집단의 특성**을 시각화하는 것이다.

---

## 2. 공모전 및 과제 조건

이 프로젝트는 두 가지 목적을 동시에 가진다.

1. **KOSSDA 대학생 데이터 시각화 공모전 2026** 제출 준비
2. **경영정보처리론 데이터 분석 및 시각화 프로젝트** 제출 준비

- **KOSSDA 공모전**: 한국 사회의 특징적인 사회현상이나 문제, 변화 및 미래 전망에 대한 데이터 기반 분석과 시각화를 요구한다. 또한 **1건 이상의 KOSSDA 소장 데이터**를 활용해야 한다.
- **수업 프로젝트**: 문제 정의, **2개 이상의 공공데이터 통합**, SQL 기반 분석, 시각화, 인사이트 도출을 요구한다. 최종 제출물에는 Streamlit 배포 주소, GitHub Repository 주소, 프롬프트 공유 링크, 발표자료가 포함된다.

따라서 이 프로젝트는 단순 분석 노트북이 아니라 다음 형태를 목표로 한다.

- Python 기반 데이터 전처리
- SQLite 기반 분석용 DB 구축
- SQL 기반 집계 분석
- Streamlit 기반 시각화 웹앱
- GitHub 기반 코드 관리
- PPT/요약문 제출을 위한 결과 정리

## 4. 데이터 역할

데이터를 무조건 많이 쓰는 것이 아니라, 각 데이터의 **역할을 명확히 분리**한다.

### 4-1. 경제활동인구조사 — 문제 제기 및 배경 설명

**분석 질문**
- 청년층에서 쉬었음 상태는 어느 정도 규모인가?
- 실업자와 쉬었음 청년은 어떻게 다른가?
- 실업률만으로 청년 노동시장 문제를 설명하기 어려운 이유는 무엇인가?

**예상 시각화**
- 청년 경제활동상태 분포
- 실업자와 비경제활동인구 비교
- 쉬었음 인구 규모 변화
- 연령대별 쉬었음 비율

### 4-2. 청년삶실태조사 2024 — 메인 분석 데이터

**분석 질문**
- 쉬었음 청년은 취업자 또는 구직자와 생활조건이 어떻게 다른가?
- 쉬었음 청년 내부에서도 경제·주거·심리·관계 조건에 따라 취약성이 다른가?
- 쉬었음 청년을 하나의 집단으로 보는 것이 적절한가?

**예상 분석 변수**
- 경제활동상태, 소득, 생활비, 부채
- 주거 형태, 부모 동거 여부
- 주관적 계층 인식, 삶의 만족도, 미래 전망
- 사회적 고립 또는 관계 관련 변수

**예상 시각화**
- 노동상태별 생활조건 비교
- 쉬었음 청년과 비쉬었음 청년 비교
- 취약성 지표별 분포
- 군집별 프로파일
- 주거·소득·부채 조건의 결합 시각화

### 4-3. KLIPS 2023 또는 최신 연도 — KOSSDA 데이터 활용 및 보조 검증

**분석 질문**
- 청년삶실태조사에서 나타난 취약성 패턴이 KLIPS에서도 일부 확인되는가?
- 청년 개인의 노동상태와 가구 조건은 어떤 관계를 가지는가?
- 청년층의 비경제활동 상태는 개인 문제라기보다 가구·소득·주거 조건과 연결되어 있는가?

**사용 방향**
- 최신 연도 개인 데이터 p 파일 우선
- 필요 시 가구 데이터 h 파일과 결합
- 전체 1998~2023 패널을 한 번에 사용하지 않음
- 코드북을 먼저 확인한 뒤 변수 의미를 확정
- 코드북 파일은 DB에 넣지 않고 **변수 해석용 참고자료로 분리**

## 5. 핵심 논리 흐름

1. 청년 문제를 실업률만으로 설명하기 어렵다.
2. 구직활동을 하지 않는 '쉬었음' 청년이 중요한 사각지대다.
3. 그러나 쉬었음 청년을 하나의 동질적 집단으로 보면 안 된다.
4. 쉬었음 청년 내부에는 경제·주거·가구·심리 조건에 따라 취약성이 다른 하위 집단이 존재할 수 있다.
5. 데이터 분석을 통해 쉬었음 청년 내부의 취약성 유형을 구분한다.
6. 이를 시각화하여 정책적·사회적 해석이 가능한 형태로 제시한다.

## 6. 분석 설계 원칙

### 6-1. 데이터 최신성
- 메인 분석은 **2023년 이후 데이터**를 우선 사용한다.
- 2020~2021년 데이터는 코로나 특수성이 강하므로 단독 메인 분석에 사용하지 않는다.
- 2022년 데이터는 비교 목적일 때만 사용한다.
- **2024년 청년삶실태조사**를 우선 메인 데이터로 사용한다.

### 6-2. KOSSDA 활용 원칙
- KOSSDA 데이터는 공모전 조건을 맞추기 위해 억지로 끼워 넣지 않는다.
- KLIPS는 **독립적인 분석 슬라이드 또는 보조 검증 결과**를 만들 수 있을 정도로 의미 있게 활용한다.

### 6-3. 변수 우선 원칙
- 데이터를 보고 주제를 끼워 맞추지 않는다.
- 먼저 연구질문에 필요한 변수 목록을 정하고, 각 데이터에서 해당 변수를 찾는다.

**필수 변수 후보**
- 연령, 성별
- 경제활동상태, 취업 여부, 구직 여부, 쉬었음 여부
- 소득, 생활비, 부채
- 주거 형태, 부모 동거 여부, 가구소득
- 삶의 만족도, 미래 전망
- 사회적 관계 또는 고립 관련 변수

### 6-4. 코드북 우선 원칙
- 데이터에 1, 2, 9, 99, 999 등의 코드값이 있을 경우 **코드북 확인 전에는 결측치 또는 응답값으로 임의 판단하지 않는다.**
- 결측 처리, 비해당 처리, 무응답 처리는 코드북 확인 후 수행한다.

### 6-5. 분석 가능성 원칙
- 분석기법은 데이터 구조에 맞게 선택한다.

**가능한 분석**
- 빈도분석, 교차분석, 집단 간 평균 비교
- SQL 기반 집계, 취약성 점수화, 군집분석
- 시각화 중심 탐색 분석

**주의**
- 데이터 구조가 확인되기 전까지 회귀분석이나 군집분석을 확정하지 않는다.
- 시각화 가능성이 낮은 분석은 우선순위를 낮춘다.

## 7. 개발 원칙

### 7-1. 원본 데이터 관리
- 원본 데이터는 GitHub에 커밋하지 않는다.
- 다음 폴더는 `.gitignore`에 포함한다: `data/raw/`, `data/processed/`, `data/db/`
- CSV, XLSX, SQLite DB 파일도 기본적으로 GitHub에 올리지 않는다.

### 7-2. 분석 파이프라인
1. `data/raw`에 원본 데이터 저장
2. `inspect_data.py`로 파일 구조 확인
3. `preprocess.py`로 1차 전처리
4. `build_db.py`로 SQLite DB 생성
5. `queries.py`로 SQL 분석
6. `charts.py`로 시각화 함수 관리
7. `app.py`에서 Streamlit 웹앱 구성

### 7-3. Streamlit 앱 방향
Streamlit 앱은 단순 결과 나열이 아니라 **분석 흐름을 보여주는 형태**여야 한다.

**권장 화면 구성**
- 프로젝트 개요
- 문제의식
- 데이터 소개
- 분석 흐름
- 경제활동인구조사 기반 현황
- 청년삶실태조사 기반 메인 분석
- KLIPS 기반 보조 검증
- 쉬었음 청년 내부 취약성 유형
- 결론 및 시사점

**초기 개발 단계 우선 구현 기능**
- DB 존재 여부 확인
- 테이블 목록 표시
- 테이블 미리보기
- 컬럼 정보 표시
- 선택 컬럼 value_counts 시각화
- 수치형 컬럼 히스토그램

### 7-4. 코드 작성 주의사항
- 실제 분석 결과를 임의로 만들지 않는다.
- sample 데이터로 결론을 꾸미지 않는다.
- 특정 파일명이나 컬럼명을 처음부터 하드코딩하지 않는다.
- Windows 환경에서도 실행 가능하도록 `pathlib`을 사용한다.
- 파일이 없거나 DB가 없을 때 앱이 죽지 않고 안내 메시지를 보여주게 한다.
- 외부 API, API key, secrets 관련 기능은 만들지 않는다.
- 데이터 규모가 커질 수 있으므로 모든 파일을 무조건 한 번에 읽지 않는다.
- 코드북 파일과 분석 데이터 파일을 구분한다.

## 10. Cursor 작업 방식

앞으로 작업할 때는 위 문서를 먼저 읽고, 프로젝트의 문제의식과 데이터 역할에 맞게 코드를 작성해야 한다.

코드를 작성하기 전에 다음을 먼저 확인한다.

- 어떤 데이터 파일을 대상으로 하는가?
- 해당 파일이 원자료인지 코드북인지?
- 해당 데이터의 역할이 배경, 메인 분석, KOSSDA 보조 검증 중 무엇인지?
- 분석 결론을 임의로 만들고 있지는 않은지?
- 원본 데이터가 GitHub에 올라가지 않도록 되어 있는지?
